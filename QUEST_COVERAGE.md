# Quest coverage — the missing-quest audit

Generated by `tools/coverage/quest_coverage.py --retail`. Re-runnable; the parser
self-validates against five known quest ids and aborts on drift.

## Why this document exists

Every quest audit on this repo so far ran **repo-inward-out**: list the files we
have, find the ones with stub markers, fix those. That method structurally cannot
find a quest that has no file at all. A stub announces itself; an absent quest is
invisible. So the "33 remaining stubs" figure everyone has been working from was
never the size of the problem — it was the size of the *visible* problem.

This audit runs the other direction, on two independent axes.

### The `Converted` column is a useful signal
`-- + Converted` in quests.lua is upstream's marker for "ported to the interaction
framework". Where an area's missing set is entirely *unconverted*, that is
consistent with never-implemented. Where a missing entry IS marked Converted, a
file existed and is now gone. crystalWar shows 27 missing of which 25 are marked
Converted — that is our own deletion history surfacing, chiefly the Voidwatch
chain (`AD_INFINITUM`, `VOIDWALKER_OP_126`, `PROVENANCE`, `GUARDIAN_OF_THE_VOID`,
`BETWEEN_A_ROCK_AND_RIFT`, …) plus the Cait Sith and Duchy campaign sets.

## Method notes that matter

**Match by declaration, never by filename.** Upstream filenames are inconsistent
(`WOTG_BAS_6_Fire_in_the_Hole.lua`, `LB04_Riding_on_the_clouds.lua`,
`MNK_AF1_Ghosts_of_the_Past.lua`), so a filename diff invents "missing" quests.
The tool reads each file's own `Quest:new(xi.questLog.X, xi.quest.id.area.NAME)`
plus `questId = ...` for table-driven helpers. This is load-bearing: validating
against the 47 quest files deleted in the current working tree, 37 were correctly
flagged and **10 were correctly NOT flagged** because the quest lives on under an
upstream filename.

**Normalisation of wiki titles must turn separators into underscores, not delete
them.** `Eco-Warrior` has to reach `ECO_WARRIOR`, not `ECOWARRIOR`. Getting this
wrong inflated the wiki-only counts by roughly 2× on the first run.

**Watch for a silent empty parse.** The first version of this parser matched the
wrong indentation, returned zero enum entries, and printed a confident table in
which *every* quest looked absent. If the totals come back at 0, the parser has
drifted — that is why `SENTINELS` exists and aborts.

## What is still not covered

* Missions. 447 mission files exist and **none** has been compared against
  bg-wiki. This audit covers quests only.
* Classifying the 408 into real log quests vs repeating system content
  (Dominion / Coalition / Voidwatch ops).
* abyssea's 22 wiki-only titles need manual reconciliation against the enum's
  suffixed names.
* `otherAreas` has no matching bg-wiki category, so it has no axis-2 check.

## !! UPSTREAM TEXT IDS DO NOT TRANSFER — VERIFY EVERY ONE !!

The single most important result of this pass. `Eco_Warrior.lua` referenced two
text ids absent from our IDs.lua. Upstream's values were checked against our own
DAT dumps before being copied, and **every one was off by exactly -3**:

| Zone | upstream id | our real id | what upstream's id actually says here |
|---|---|---|---|
| Gusgen Mines (196) | 7426 | **7423** | "Items, items, la la la la la~" |
| Maze of Shakhrami (198) | 7323 | **7320** | "The hairs on the back of your neck stand on end!" |
| Ordelles Caves (193) | 7456 | **7453** | "Items, items, la la la la la~" |

Copying upstream's numbers would have shipped three quests printing unrelated
lines, with nothing failing loudly. The client-version hazard already known for
CSIDs applies to **zone text ids too**. Any file pulled from upstream must have
every id it introduces re-verified with
`xi-dat search <zone> "<phrase>"` / `xi-dat dialog <zone> <id>`.

Note the safe case: ids whose NAME already exists in our IDs.lua resolve to *our*
value and are fine. Only newly introduced names carry this risk.

### Other adaptations the pull needed
* `xi.cutsceneFlag.RESET_CAMERA` does not exist in our enum. Our older enum names
  the same bit `UNKNOWN_1`, and both are `0x0001` — upstream renamed it once its
  effect was understood. Adapted to our name rather than adding a second key for
  one bit value.
* No NPC or mob data was missing. `Necroplasm` (z193), `Pudding` (z196),
  `Wyrmfly` (z198), `Bugaboo` (z150), `Yum_Kimil` (z195) and `Enagakure`
  (z220/227) are all present in exactly the zones the quests bind — they are mobs
  bound via `onMobDeath`, so check `mob_spawn_points.sql`, not `npc_list.sql`.

All 8 pass `luac -p`, stylecheck, `lua_binding_usage`, and a full
symbol audit covering enums, quest ids and text ids.

## CORRECTION to the Assault section above, and the fix applied

The claim above that "`instance_list.sql` carries only **10 rows** for the six
Assault zones" is **wrong**, and so is the conclusion drawn from it. That number
came from grepping instance_list by ZONE NAME, which silently misses every row
whose `instance_name` does not contain its zone — `requiem`, `extermination`,
`golden_salvage`, `troll_fugitives`, `preemptive_strike` and others. Counted
properly, by `instance_zone` id:

| Zone | active rows | commented rows |
|---|---|---|
| Ilrusi Atoll (55) | 3 | 7 |
| Periqia (56) | 3 | 7 |
| Lebros Cavern (63) | 6 | 3 |
| Mamool Ja Training Grounds (66) | 3 | 7 |
| Leujaoam Sanctum (69) | 2 | 8 |
| Nyzul Isle (77) | 4 | 2 |
| **TOTAL** | **21** | **34** |

So entry data was never the bottleneck — every one of the 19 Assault instance
scripts already had an active row. The real state is **19 implemented of ~55
defined**, and the 34 commented rows (all with `0.000/0.000/0.000` placeholder
coordinates) are the backlog.

### The actual defect found: 2 dangling active rows

Two rows were ACTIVE with no instance script behind them. Since `luautils.cpp:2047`
resolves an instance through `scripts/zones/<Zone>/instances/<name>.lua`, and both
assaults exist in `xi.assault.mission`, a player could register either at the
staging point and then be unable to enter — a dead end, not a loud failure.

Both had **real researched start coordinates**, unlike the 34 placeholder rows,
so they were "data ready, script missing" and were treated individually:

* **`lamia_no_13` (5501) — BUILT.** All mob data was already present:
  `mob_pools` 2340 'Lamia_No13' (family 171), `mob_groups` (3, 2340, **zone 55**,
  respawn 0 = pop-only), `mob_spawn_points` 17002517 at
  (24.381, -4.094, -209.261) rot 42, level 77-78. And
  `scripts/enum/assault.lua` already had `LAMIA_NO_13 = 42` with
  `{ suggestedLevel = 70, minimumPoints = 1200 }` — matching bg-wiki's
  "Lvl. 70 / Points3=1200" exactly. Added
  `scripts/zones/Ilrusi_Atoll/instances/lamia_no_13.lua`,
  `scripts/zones/Ilrusi_Atoll/mobs/Lamia_No13.lua` (bumps instance progress on
  death; single objective, completes at 1) and the `MOBS_START` block in that
  zone's `IDs.lua`. Rune of Release / Ancient Lockbox positions are a documented
  guess — cosmetic, cannot block completion.
* **`orichalcum_survey` (6901) — commented out.** Genuinely unbuildable: bg-wiki's
  objective is "Discover Orichalcum Ore" with Mineral Worms as enemies, and
  `Mineral_Worm` appears in **none** of mob_pools, mob_groups or
  mob_spawn_points. Commented rather than deleted so the coordinates survive. The
  ten `Mining_Point` NPCs (17060016-17060025) that would be the ore veins DO
  already exist in zone 69, so this needs only the Mineral Worm mob data.

Result: **20 active Assault rows, 20 scripts, zero dangling.**

# THIRD CORRECTION — the 408 over-counts, and the 8 upstream pulls were reverted

## The upstream pulls created ~30 double-reward sites. All 8 reverted.

`scripts/globals/interaction/interaction_lookup.lua:410-421` runs **both** the
Interaction-Framework handler **and** the legacy zone-NPC fallback. The exclusion
list is only `onSteal` / `onTrigger` / `onTrade` — `onEventFinish` is deliberately
NOT excluded ("Most handlers should run both the handler system and fallback if
available"). `npcUtil.completeQuest` has no already-completed guard.

That design assumes the legacy per-NPC script has been REMOVED when a quest is
converted. Upstream does exactly that — `Port_Bastok/npcs/Raifa.lua`,
`Southern_San_dOria/npcs/Norejaie.lua` and `Windurst_Waters/npcs/Lumomo.lua` are
all **absent from upstream/base**, and upstream's `Jatan-Paratan.lua` is reduced to
idle chatter (csids 610/611/615) with no quest logic at all.

Our repo still had the full legacy implementations, tracked in HEAD and working.
Pulling upstream's quest files on top of them produced quest-file + legacy-script
both handling the same csids. Every one of the 8 pulls was affected:
